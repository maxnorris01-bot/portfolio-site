## Decisions
- Errors: 400 `invalid_body|invalid_name|invalid_email|invalid_message`, 429 `rate_limited` (with Retry-After), 503 `unavailable`, 500 `send_failed`. Logs carry only `contact: unavailable` or `contact: send_failed`.
- The portfolio-site has no database connection, so limits are in memory. A visitor is the first `x-forwarded-for` address, hashed with a random per-instance salt; no raw address or message text is kept.
- A header-injection attempt in the name is neutralised (control characters stripped); in the email it is refused (400), since the leftover text is not a valid address.
- A filled honeypot gets 200 `{ok:true}` before any field is judged, and is not counted.
- The Gmail address exists only as an env var on the server. The PDF in `public/` still contains it (owner's choice).

## Limits
- Rate limits are best effort: per function instance, reset on a cold start, not shared between instances. The real ceiling is therefore higher than 30 a day when several instances run. A shared store (Vercel KV or Neon) would make them exact.
- Not tested against real Gmail (no credentials used).

## Test it once the env vars are set
1. In Vercel (Production and Preview) set `CONTACT_GMAIL_USER` and `CONTACT_GMAIL_APP_PASSWORD` (app password from the Google account, 2-step verification on); redeploy.
2. Open the site, press Contact, send a message. It should arrive from "Portfolio contact" with Reply-To set to the email you typed.
3. Locally: `CONTACT_GMAIL_USER=... CONTACT_GMAIL_APP_PASSWORD=... npm run dev`, then use the form. Without them the form shows "Contact is temporarily unavailable."
