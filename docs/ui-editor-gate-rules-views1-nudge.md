Question: **do the Nudge X and Nudge Y boxes move an element the way a drag does (one custom rule for the view they are made in), and does every nudge give a change or a visible reason?**

## 1. What the probe shows (read-only, before any change; `probe-nudge-views1.mjs`, headless Chromium, the three samples, five elements each, three views, an arrow click, a typed 10 and a 20 px drag; `main` at `05d80d9` and the branch at `48f7507`)
- **Desktop nudge is a plain edit on both `main` and the branch.** The page sends `{op:'offset', environment:'desktop'}` with no `link:false` (`scope()` carries none), the engine reads it as linked (`isCustomEdit` false) and writes one inline translate or a rule edit that applies at EVERY width: the element moves at 1280, 768 AND 390 (Phone too) for the 12 elements that moved at all. A Desktop drag is custom (`link:false`): 1280 and the tablet range, not Phone. The two differ.
- **A nudge can be a silent no-op.** (a) After a Desktop (plain) nudge a Tablet or Phone nudge of the same element is "Applied" but nothing moves in that view (landing `#headline`: Tablet and Phone nudge after a Desktop nudge move nothing at 1280, 768 or 390). (b) After a Desktop nudge of the email heading the Tablet and Phone nudges are refused with `inline-conflict` (this one is shown). (c) On `main` the Tablet boxes are disabled (view-only).
- **Selecting:** in 18 of 135 rows the probe's click selected a child (`#card-plan`'s paragraph, the chart's `#axis` under a bar): a probe limit, listed, not a page fault.
- On the branch a Phone or Tablet nudge alone works (moves only its own range) for every element tried.

The cause is the scope mismatch of the brief plus one more thing it did not name: **(1)** the nudge is not custom on Desktop; **(2)** the page never checks that the element moved, so an edit that shows nothing is reported as applied.

## 2. Expected behaviour (the brief's six points, mine to measure)
1. A Desktop nudge is the same kind of edit as a Desktop drag: `{op:'offset', environment:'desktop', link:false}`, one rule for the widths above the phone breakpoint (the tablet range included); the status line names the widths as the drag does ("Desktop and Tablet sizes", or "Desktop only" when the page has no tablet band). It never moves the element in Phone.
2. A Tablet or Phone nudge moves only that view (`{environment}` alone). Desktop then Phone, Phone then Desktop and Desktop then Tablet all work and neither changes the other view's position (measured at 1280, 1025, 1024, 768, 641, 640, 390); a nudge is relative to what its view shows, so a Tablet nudge after a Desktop one shows both (K07).
3. Repeated nudges of one element in one view are one merged edit (the page's existing merge of consecutive offsets of one scope): no pile of rules.
4. Every refusal shows its plain reason in the status line in the same event and adds nothing to the edit list or Undo. **(mine)** "No silent no-op": a nudge after which the element's box (left, top) in the view it was made in is unchanged (less than 0.4 px) is not kept: the preview is built again from the list and the status line says "Not applied: that element does not move when it is shifted at this size (a table cell, for example, ignores a shift), so nothing was changed." An engine refusal keeps the engine's own reason.
5. Typing and the arrow both work; a typed 0 or a non-number changes nothing and says nothing wrong.
6. Undo and Redo restore the exact bytes. Flag OFF identical. Drags are unchanged; Move up and Move down are untouched.
